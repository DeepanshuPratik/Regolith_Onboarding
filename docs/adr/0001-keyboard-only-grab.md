# Keyboard-only seat grab, and the user as the re-grab recovery path

Observation on GNOME/KDE Wayland works only through a **keyboard-only** `Gdk.Seat.grab()`: GTK3 requests `zwp_keyboard_shortcuts_inhibit_v1` for a keyboard grab but silently emits no protocol traffic at all for `KEYBOARD | POINTER`. So every grab site asks for `KEYBOARD` alone. The consequences that make this surprising without context: a re-grab after focus has been lost is inert (and every status/focus signal lies), Mutter refuses `xdg_activation_v1` so the app cannot take focus back, and the re-grab works only while focus stays put — so on GNOME the recovery path is the **user** clicking back into the window, with a timeout driving a visible prompt, not anything the app can do from inside the process. The shortcuts-inhibitor wakes up by itself once focus genuinely returns, so no second consent dialog is needed.
