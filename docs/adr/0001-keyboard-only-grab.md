# Keyboard-only seat grab, and the user as the re-grab recovery path

Observation on GNOME/KDE Wayland works only through a **keyboard-only** `Gdk.Seat.grab()`: GTK3 requests `zwp_keyboard_shortcuts_inhibit_v1` for a keyboard grab but silently emits no protocol traffic at all for `KEYBOARD | POINTER`. So every grab site asks for `KEYBOARD` alone — and there is now exactly one: `SeatGrabObserver` takes it at PLAY and drops it when the workflow ends. The toplevel's own map-time grab was deleted (#29); it asked for `KEYBOARD | POINTER`, which made the inhibitor unobtainable on an XWayland connection into Mutter or KWin, held the keyboard for the whole run, and aborted startup when it failed. The consequences that make this surprising without context: a re-grab after focus has been lost is inert (and every status/focus signal lies), Mutter refuses `xdg_activation_v1` so the app cannot take focus back, and the re-grab works only while focus stays put — so on GNOME the recovery path is the **user** clicking back into the window, with a timeout driving a visible prompt, not anything the app can do from inside the process. The shortcuts-inhibitor wakes up by itself once focus genuinely returns, so no second consent dialog is needed.
